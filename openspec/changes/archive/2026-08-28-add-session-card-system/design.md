# 设计：次卡体系

## Context

现有三层架构：预约（纯排班）→ 服务模板（大类 → 基础项目/附加项目，含价格、折扣/提成标志）→ 结算（服务端重算金额，实收确认收入，生成积分/提成）。储值折扣卡已账户化。用户已拍板：次卡核销规则建卡种时配置；每次结算固定核销 1 次；收入以核销为准（次卡与储值卡同为预收），报表区分预收未核销；提成按折算价核销时计提；积分核销时给。

## Goals / Non-Goals

- Goals：卡种可配置核销规则；结算集成核销；预收/已核销财务区分；退卡留痕。
- Non-Goals：次卡转让/赠予；跨店通用；线上售卡；次卡与储值卡互转；有效期自动任务过期扫描（核销时惰性判定即可，列表展示时按当前时间计算状态）。

## Decisions

### 单次折算价

- 决策：`sessionValue = floor(售价 / 总次数)`（分），开卡时快照到会员次卡。
- 理由：整数分避免精度问题；整除不尽时的零头差异由门店承担（如 ¥680/10 次 = 68 元整）。
- 备选：最后一次补足差额——被否，增加判定复杂度，金额差异可忽略。

### 核销匹配判定（服务端）

- 决策：依次校验 ①卡 status='active' ②未过期（expiresAt 为空或 > 当前时间）③剩余次数 > 0 ④卡种适用大类 === 结算大类 ⑤覆盖范围为 all 或结算基础项目在指定清单内。全部通过才允许核销。
- 附加项：卡种配置了 `coveredAddonIds` 时，命中附加项金额一并从应收扣除；未配置或附加项不在清单内的一律另收费。

### 结算金额处理

- 决策：服务端重算时，被次卡覆盖的项目金额不计入应收；消费记录快照中这些项目标注 `paidBySessionCard: true` 并记录 `sessionCardRedemptionId`。支付明细校验仍要求支付总额 = 实收（扣除次卡部分后的金额）。
- 次卡覆盖部分不参与储值卡折扣（折扣金额只按现金收费部分的可折扣项目计算）。

### 财务与提成、积分

- 收入：核销流水 `session_card_redemptions` 记录 `recognizedAmount = sessionValue`；财务「核销确认收入」= 结算实收 + 期内次卡核销折算价？——否：**核销项目的收入已含在结算单口径中**（消费记录照常生成，金额按折算价计入总收入需单独汇总）。决策：财务页新增独立区块展示「本期次卡核销确认收入」「预收未核销余额（储值卡余额 + 次卡剩余价值）」「本期新增预收（充值 + 售卡）」，不改动现有总收入口径（仍按结算实收），避免历史报表断裂。
- 提成：核销时生成提成记录，金额 = `floor(sessionValue × 技师提成比例)`，source 标记为 `session_card`。
- 积分：核销时给会员加积分 = `sessionValue ÷ 100 × 10`（每 1 元 10 积分，整数分取整）。
- 储值卡口径不变：充值计预收，结算用卡支付时已按实收确认收入（与现状一致），无需改动结算逻辑。

### 有效期

- 决策：卡种配置 `validityType: 'permanent' | 'days' | 'fixed_date'`；开卡时计算 `expiresAt` 快照。过期判定惰性化：核销与查询时按当前时间比较，不建定时任务。

### 退卡

- 决策：仅超管；`refundPolicy: 'none'` 直接拒绝；`'prorated'` 退款额 = 剩余次数 × 单次折算价，实退金额允许管理员修改（默认折算额），必填原因；卡置 `refunded`，余额次数清零留档，写操作日志。退款走线下，系统只留痕。

## Risks / Trade-offs

- 卡种修改不影响已售卡（快照）→ 报表按快照折算价统计，与卡种现价可能不一致：可接受，审计优先。
- 核销与结算同事务语义不可达（NoSQL 无多文档事务）→ 顺序写：结算记录 → 卡扣次 → 核销流水 → 提成/积分；失败重提由前端报错后人工处理，概率低。
- 预收统计为全表聚合 → 数据量级小（单店），可接受。

## Migration Plan

- 新集合无需迁移；`initDatabaseIndexes` 补充 `member_session_cards(memberId, status)`、`session_card_redemptions(cardId, createdAt)` 索引。
- 部署顺序：云函数 → 索引初始化 → 前端。
- 回滚：次卡功能开关（无卡种即无入口），回滚云函数即可，已核销数据保留。
